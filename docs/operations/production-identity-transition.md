# Production identity transition

The current public site uses Clerk development authentication. The owner confirmed on 3 November 2026 that no custom domain has been purchased. Keep existing login working until the following transition is reviewed and tested. This document does not authorize a domain purchase or a production identity migration.

1. Choose an owned domain and obtain DNS management. Configure the domain in the existing `axon-frontend-vxa8` Vercel project; keep its canonical Vercel URL available during transition. Clerk's production deployment requires an owned domain and DNS setup. See [Clerk production deployment](https://clerk.com/docs/guides/development/deployment/production).
2. Create the corresponding production Clerk instance. Review signup/email verification, bot/abuse controls, allowed redirect origins, session settings, OAuth provider production credentials and required DNS entries. Production creation does not establish that all development settings/users/metadata have been copied.
3. Plan identity continuity before changing keys: inventory user IDs referenced by account quotas, API-key owners, jobs, reviews, callback destinations, privacy requests, checkout records, Clerk private metadata and Razorpay subscription notes. Use a reviewed, verified mapping and recovery procedure. Never merge identities solely from an unverified email, reset Free usage, alter paid periods or assign an existing subscription to a new user by assertion. No automated migration is prepared without the domain and final identity plan.
4. Test production-instance sign-in with controlled accounts on the chosen host and exact authorized-party origins. Verify correct existing plan, usage, key management, callback ownership and sandbox-equivalent lifecycle contracts. Real users must not lose entitlement while the frontend and server use different instances. Preserve rollback configuration securely; never include keys in a report or Git.
5. Deploy paired public/server production Clerk keys together only after the identity continuity plan is approved and validated. Set `AXON_PUBLIC_SITE_URL` to the chosen canonical HTTPS origin, review all payment/webhook and contact links, and verify protected routes reject foreign origins. Existing server-origin guards and Clerk authorized parties must agree. Razorpay's existing canonical webhook must continue working throughout; changing a hostname alone must not create duplicate event work.
6. Confirm canonical public pages and signed-in account management, current paid account access, and provider webhook deliveries. Record the actual production key mode and instance issuer without secret values. Keep the old site/login rollback available until acceptance is complete.

Until then: restricted, honestly described beta with existing login; do not mark full production identity setup complete or advertise enterprise-grade availability.
